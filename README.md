# Wealth Portfolio NLQ — AtScale SML model

Client Portfolio Performance & Allocation semantic model for a Merrill Lynch-style
wirehouse advisory book, generated by the `atscale-sml-model-generator` skill.

## Inputs

- `context/use_case.md` — use case: personas (advisors/clients), 5 brief NLQs, engineered
  narratives (diversification vs index, allocation drift, tech concentration, realized/unrealized
  gains, segment AUM tiers), grain table, and known limitations. NLQs are embedded in this doc.
- `context/02_ddl.sql` — Databricks SQL / Delta (Unity Catalog) DDL: 6 dimension tables + 4 fact tables.
- `context/erd.mmd` — Mermaid ERD confirming relationships and cardinality (incl. `dim_account }o--|| dim_model_target`).
- `context/data_profile.yaml` — column-level profile (row counts, distincts, min/max) used to derive `is_unique_key` (Rule 16).
- NLQs — embedded in `context/use_case.md` (no separate file).
- Target warehouse — Databricks / Delta (derived from the DDL header and identifier casing).

## Build parameters

- `unrelated_dimension_handling` = `repeat` — applied to every base metric (Rule 3).
- `warehouse` = Databricks (lowercase storage case, Rule 1).
- `model_unique_name` = `wealth_portfolio_nlq`.
- `catalog_unique_name` = `wealth_portfolio_nlq_catalog` (Rule 8c).
- `currency` = USD (single currency per use case).
- `time_window` = calendar (monthly month-end; no fiscal/retail markers).
- `use_cases_covered` = NLQ1 performance-vs-benchmark, NLQ2 allocation drift, NLQ3 asset/sector exposure,
  NLQ4 realized vs unrealized gains, NLQ5 household AUM by advisor.
- `use_cases_excluded` = net flows / net-new-assets (use case marks `net_flow = 0`, out of scope).
- `semi_additive_default` = `last_non_empty` for snapshot facts (position, performance, benchmark, allocation drift);
  `sum` for the transactional realized-gain fact.

## Assumptions and decisions

- **warehouse = Databricks** — DDL header says "Databricks SQL / Delta, Unity Catalog" and all identifiers are lowercase; identifiers emitted lowercase (Rule 1).
- **connection database/schema = main / wealth_portfolio_nlq** — the DDL parameterizes catalog and schema; defaulted to a Unity Catalog `main` catalog and the dataset-named schema. Adjust the connection file to your workspace. (Branch `snowflake` points at Snowflake instead; see below.)
- **Date is role-played as `As Of {0}` and `Sold {0}`** — `snapshot_date` (position, performance, benchmark, drift) is an as-of axis; `sell_date` (realized gain) is a transaction axis. Two semantically distinct date FKs → two roles (Rule 2/4).
- **Account Dimension is one snowflaked dimension** — Advisor > Household > Account span dim_advisor/dim_household/dim_account joined intra-dim (Rule 5); not three separate dimensions.
- **Security Sector level is composite-keyed `(asset_class, sector)`** — the `'-'` sector value is shared by Fixed Income/Cash/Alternative; a single-column key would collapse them and break rollup. Composite key keeps Asset Class > Sector > Security valid.
- **`dim_model_target` has no standalone dataset** — its join path (account.risk_model → model_target.model AND security.asset_class → model_target.asset_class) runs through two dimensions and is one-to-many, so it cannot be a star/snowflake FK. It is consumed only inside the `fact_allocation_drift` query dataset (Rule 15). No unreferenced dataset emitted.
- **`fact_allocation_drift` is a SQL query dataset (Rule 15)** — computes actual asset-class weight (windowed share-of-total) minus target_pct at (account × asset_class × month); joins the Security dimension at the Asset Class rollup level. Drift metrics are semi-additive last-non-empty over date; percentage-point columns are formatted as plain numbers (not `percent`).
- **Benchmark and Term are degenerate dimensions** — `benchmark_id`/`benchmark_name` live on fact_benchmark_return; `term` lives on fact_realized_gain. `is_degenerate: true`, no `type:`, listed in the model `dimensions:` block, no `is_unique_key` (Rule 12/16).
- **`is_unique_key` derived from the data profile (Rule 16)** — set true only where `distinct == row_count`: Date.Month (date_id 36/36), Account (3315/3315), Household (1500/1500), Advisor (60/60), Security (360/360). Omitted on Year/Quarter/Asset Class/Sector and all degenerate keys.
- **Net flow / monthly_return** — `net_flow` column retained (defined in the dataset) but no metric emitted; the use case marks net flows out of scope. `monthly_return` exposed as an `average` metric in percent points.
- **calc role-play follows the verb (Rule 4)** — "Realized Gain Year to Date" uses the Sold axis; "Unrealized Gain Prior Year" and "Market Value Prior Year" use the As Of axis. Prior-year calcs use `ParallelPeriod` + `parallel_periods` blocks on Quarter/Month + a `prior_year_num` column (Rule 13), never `Lag(12)`.

## Generation summary

- **Datasets:** 10 (5 dimension tables + 4 fact tables + 1 allocation-drift query dataset). `dim_model_target` intentionally has no dataset.
- **Dimensions:** 5 — Date (time, role-played As Of/Sold), Account (snowflake Advisor>Household>Account), Security (Asset Class>Sector>Security), Benchmark (degenerate), Term (degenerate).
- **Base metrics:** 18, all with `unrelated_dimensions_handling: repeat`. Snapshot metrics (position, performance, benchmark, drift) are semi-additive `last` over the As Of date.
- **Calculated metrics:** 3 — Realized Gain YTD (PeriodsToDate, Sold axis), Unrealized Gain Prior Year + Market Value Prior Year (ParallelPeriod, As Of axis).
- **Model relationships:** 12.
- **Role-play prefixes on Date Dimension:** As Of, Sold.
- **Snowflake bridges:** Account Dimension (dim_account→Household, dim_household→Advisor), both visible.
- **Calculated columns added:** `prior_year_num` (dim_date, Rule 13); `realized_loss` / `realized_profit` (fact_realized_gain, NLQ4 sign split).
- **NLQ coverage:** NLQ1 Benchmark Monthly Return + Monthly Return vs Benchmark dim; NLQ2 Allocation/Absolute Allocation Drift Pct via the query dataset; NLQ3 Market Value by Asset Class/Sector; NLQ4 Unrealized Gain + Realized Gain/Loss/Profit + Realized Gain YTD; NLQ5 Market Value by Household/Segment with Advisor rollup.
- **Caveats:** drift/percentage-point metrics use `sum` aggregation and are meaningful per (account × asset_class); a true "S&P-beating accounts" count (NLQ1) is a ranking that the Account-level Monthly Return vs Benchmark Monthly Return comparison supports by inspection rather than a TopCount calc (unsupported in AtScale MDX).

## Snowflake version (branch `snowflake`)

The `snowflake` branch runs the same model on Snowflake, for the Morgan Stanley Wealth demo.

- **Data:** Snowflake `SE_DEMO_LIBRARY.WEALTH_PORTFOLIO_NLQ` (account CK01391), loaded from the
  bundle with its Snowflake loader (Drive: `wealth_portfolio_nlq_snowflake_loader.zip`). Tables were
  created unquoted, so table and column names are UPPERCASE.
- **Connection:** `as_connection: Snowflake Partner`, database `SE_DEMO_LIBRARY`, schema
  `WEALTH_PORTFOLIO_NLQ`. Change `as_connection` to the target instance's Snowflake connection id.
- **Names:** every dataset table and column name, and every column reference in dimensions,
  metrics and relationships, is uppercase to match Snowflake. Object `unique_name`s are unchanged.
- **`fact_allocation_drift`:** the default `sql` is now Snowflake SQL with fully qualified tables
  (`SE_DEMO_LIBRARY.WEALTH_PORTFOLIO_NLQ.<TABLE>`; a derived dataset is not resolved against the
  connection's database/schema) and uppercase output aliases. The `DatabricksSQL` dialect block
  is unchanged.
- **Added calculations:** `Market Value Prior Period`, `Market Value Change vs Prior Period`,
  `Market Value Change Pct vs Prior Period` (prior quarter when grouped by As Of Quarter; uses
  `PrevMember` on the As Of hierarchy) and `Cash Share of Market Value` (Cash asset class over all
  asset classes).
- **Not answerable from this data:** households spanning more than one advisor (each household
  has exactly one advisor), net new assets (`net_flow` is 0 in every row), fee-based ROA, advisor
  attrition and branch-level security (no fee, hire/termination or branch data).

## Reproducing this build

`context/` holds verbatim copies of every input the skill consumed (use case, DDL, ERD, data profile).
No `build.yaml` was supplied; every build parameter above was derived from the inputs + documented defaults
and logged under "Assumptions and decisions". Re-running the skill with the same `context/` inputs and the
same build parameters should produce an equivalent model.
